# ADR 0001: Go のサーバに React の SPA を埋め込み、同一オリジンで配信する

## Status

Accepted

## Context

AtCoder の問題を反復学習するための Web アプリを作る。
最初から一般公開し、複数のユーザーがそれぞれの復習リストを持つ。

サーバ側では次の処理が必要になる。

- ユーザーごとの復習データ (復習する問題や解き直しの履歴) を保存する
- 間隔反復などで「次にいつ解き直すか」を計算する

画面はログイン後の操作が中心で、検索エンジンに載せたいページはほとんどない。

認証の方式はまだ決めていないが、Cookie を使う場合、画面と API のオリジンが分かれていると扱いが難しくなる。
CORS で credentials を許可する設定が必要になり、Cookie には `SameSite=None; Secure` を付けなければならない。
さらに別ドメインの API が発行する Cookie はサードパーティ Cookie になり、Safari など一部のブラウザではブロックされる。

## Decision

フロントエンドとバックエンドを 1 つのリポジトリで管理する。
本番ではフロントのビルド結果を Go のバイナリに埋め込み、API と同じオリジンから配信する。

### 構成

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| バックエンド | Go + Gin | 軽量で起動が速く、メモリ消費も少ない |
| フロントエンド | React + TypeScript + Vite (SPA) | SSR が不要。Vite は開発サーバの起動とホットリロードが速い。React はライブラリと情報が多い |
| 配信 | `go:embed` で Go のバイナリに埋め込む | API と画面が同一オリジンになる |
| リポジトリ | モノレポ (`backend/`, `frontend/`) | 画面と API の変更を 1 つのコミットで扱える |

### 開発時と本番の動き

- 開発時: Vite の開発サーバと Go のサーバを別々に起動する。`/api` へのリクエストは Vite の転送設定で Go に送るので、ブラウザからは同一オリジンに見える
- 本番: `make build` で `frontend/dist` を `backend/internal/web/dist` にコピーし、`go:embed` で 1 つのバイナリにまとめる。`/api` 以外で該当するファイルがない画面遷移には `index.html` を返し、ルーティングは React 側で扱う

デプロイ先と認証の方式は、この ADR では扱わず、別の ADR で決める。

### 採用しなかった案

#### フロントを別のホスティングに置く (Vercel / Cloudflare Pages など)

静的ファイルを CDN から配信でき、フロントだけを独立してデプロイできる。
一方で API とオリジンが分かれるため、Context に書いた CORS と Cookie の問題が起きる。
画面と API のサブドメインを揃えれば避けられるが、独自ドメインの用意と設定が増える。

#### Next.js でフルスタックにする

画面と API を TypeScript だけで書ける。
しかし、このアプリでは SSR を使う場面がほとんどなく、Next.js の主な利点を活かせない。
また、サーバの処理は軽量な Go で書きたい。

## Consequences

### Pros

- API と画面が同一オリジンになるため、CORS の設定が要らない。Cookie を使う場合も `SameSite=Lax` のまま扱える
- デプロイするものが 1 つのバイナリで済み、フロントと API のバージョンがずれない
- 開発時は Vite のホットリロードをそのまま使える

### Cons

- フロントだけを変更した場合も、バイナリを作り直してサーバごとデプロイする必要がある
- 静的ファイルを CDN のエッジから配信しないため、遠い地域からは読み込みが遅くなりやすい。必要になったら CDN を前段に置く
- フロントと API を別々にスケールできない
- ビルドは「フロントのビルド → 埋め込み用ディレクトリへのコピー → Go のビルド」の順に行う必要があり、手順を Makefile で管理する
- フロントの環境変数 (`VITE_*`) はビルド時に埋め込まれるため、実行時の環境変数では切り替えられない
- モバイルアプリなど Web 以外のクライアントを追加するときは、同一オリジンの前提が使えないため、認証と CORS を改めて設計する必要がある
