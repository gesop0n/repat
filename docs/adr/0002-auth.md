# ADR 0002: Supabase Auth でログインし、Go の API は JWKS でアクセストークンを検証する

## Status

Accepted

## Context

復習リストはユーザーごとに持つため、ユーザー登録とログインが必要になる。
DB には Supabase を使うので、認証も同じプロジェクトの Supabase Auth に任せたい。

[ADR 0001](0001-tech-stack.md) で、画面は Go のバイナリに埋め込んだ SPA として API と同じオリジンから配信すると決めた。
SSR はしないので、画面を返す時点でサーバがログイン状態を知る必要はない。

ログイン方法は次の 2 つにする。

- メールアドレスとパスワード
- GitHub (AtCoder の利用者は GitHub のアカウントを持っていることが多い)

メールアドレスの確認は行わない。

## Decision

### ログイン

ブラウザで supabase-js を使い、Supabase Auth と直接やり取りする。
登録・ログイン・ログアウト・トークンの更新は supabase-js に任せる。

- メールとパスワード: `signUp` / `signInWithPassword`
- GitHub: `signInWithOAuth` で GitHub に移動し、`/auth/callback` に戻ってくる
- OAuth は PKCE フローにする。戻ってきた URL にはトークンではなく code が載り、supabase-js が初期化時にセッションと交換する

### API の認証

API を呼ぶときは、アクセストークン (JWT) を `Authorization: Bearer` ヘッダに付ける。
Go の API はリクエストごとに次を検証し、`sub` をユーザー ID として扱う。

| 項目 | 期待する値 |
| --- | --- |
| 署名 | JWKS (`<SUPABASE_URL>/auth/v1/.well-known/jwks.json`) の公開鍵で検証できる |
| `alg` | `ES256` または `RS256` |
| `iss` | `<SUPABASE_URL>/auth/v1` |
| `aud` | `authenticated` |
| `exp` | 必須で、期限内 |

JWKS は起動時に取得し、10 分ごとに取得し直す。
Supabase はエッジとクライアントで 10 分ずつキャッシュするとしており、失効させた鍵を長く使い続けないようにするため。
JWKS が空のとき (共有シークレットの HS256 で署名しているプロジェクト) は起動に失敗させる。

ライブラリは `golang-jwt/jwt/v5` と、JWKS の取得と更新を行う `MicahParks/keyfunc/v3` を使う。

### アプリ側のユーザー

ログイン情報は Supabase Auth の `auth.users` が持つ。
アプリ側のユーザー情報は `profiles` テーブルに持ち、`auth.users(id)` を参照する。
`profiles` の行は、ログイン後に画面が最初に呼ぶ `GET /api/me` で作る (`insert ... on conflict do nothing`)。

### 採用しなかった案

#### Go がログインを代行し、HttpOnly Cookie でセッションを持つ (BFF)

トークンを JavaScript から読めない場所に置けるため、XSS で盗まれにくい。
一方で、トークンの更新や OAuth のリダイレクトの処理を Go で書き直すことになり、supabase-js の機能を使えなくなる。
Cookie を使うと CSRF への対策も必要になる。

#### `auth.users` のトリガーで `profiles` の行を作る

Supabase のドキュメントでよく使われる方法で、登録と同時に行ができる。
しかし、アプリのロジックが Supabase の管理する auth スキーマに入り込み、Go から追えなくなる。

#### Go の API が毎回 Supabase Auth の `/auth/v1/user` を呼んでトークンを確かめる

失効したセッションもすぐに弾けるが、すべてのリクエストで Supabase Auth への通信が増える。

## Consequences

### Pros

- 登録・ログイン・トークンの更新を自前で実装しなくてよい
- Bearer トークンは自動で送られないため、CSRF への対策が要らない
- API はトークンをローカルで検証するので、リクエストごとに Supabase Auth へ問い合わせなくてよい

### Cons

- アクセストークンは localStorage に入るため、XSS があると盗まれる。CSP などで XSS を防ぐ必要がある
- ログアウトしたり、ユーザーを削除したりしても、発行済みのアクセストークンは期限 (既定で 1 時間) まで使える
- メールアドレスを確認しないので、他人のメールアドレスでも登録できる。パスワードの再設定などでメールを送るようになったら、確認を有効にするか見直す
- Supabase のプロジェクトで非対称の署名鍵 (ES256 など) を有効にしておく必要がある
- 本番のダッシュボードでも、ローカルの `supabase/config.toml` と同じ設定 (メールの確認を無効、GitHub のプロバイダ、リダイレクト先の URL) をする必要がある
